# Welo · Absenteeism Analytics Mockup

A presentation dashboard for Welo's absenteeism intelligence, **wired to the real
absenteeism model output**. Every headline number, risk band, fatigue segment,
cohort breakdown and individual prediction on the page is generated by the model
in [`model/`](model/), not hardcoded.

Open [`index.html`](index.html) in a browser. It hydrates itself from
`model/data/outputs/dashboard_feed.js`. If the feed is missing it still renders
with the designed fallback numbers, so it never breaks for a screenshot.

## Industry versions

The same dashboard engine serves several industry framings, selected by a query
param so there is only one file to maintain:

| URL | Version |
| --- | --- |
| `index.html` | Industrial, sector neutral (default) |
| `index.html?industry=mining` | Mining |
| `index.html?industry=manufacturing` | Manufacturing |
| `index.html?industry=logistics` | Logistics |
| `index.html?industry=hospitality` | Hospitality (hotels, restaurants, contract catering) |
| `index.html?industry=generic` | Cross-industry, no sector wording |

**The default is the sector-neutral industrial version**, and that is the one
that goes to prospective buyers. It is blue collar wording that fits any
employer with a shift-based frontline workforce: plants, a distribution centre,
a depot, and absence that has to be covered on the day. A demo framed as one
vertical asks every other buyer to do the translating, so the verticals are
profiles rather than the baseline. The markup defaults carry the neutral wording
too, so a failed config load degrades to neutral rather than to a vertical.

Each version also carries its own accent colour (industrial and mining keep the
Welo brand red, generic teal, manufacturing steel-blue, logistics indigo) so the
pages are visibly distinct. Hospitality uses plum. The recolour only touches the brand ramp; risk-band
colours stay constant for consistent semantics.

**Manufacturing, logistics and hospitality have their own sector-calibrated
data**, not just different copy. Each loads its own `dashboard_feed.<sector>.js` generated from a
synthetic cohort whose input distributions are calibrated to that sector's
workforce norms (see below). The `industrial`, `mining` and `generic` profiles
share the base feed, which is the one the model was actually fitted on.
Industry-variable copy is tagged with `data-ind` in `index.html` and supplied
per profile in [`config/industry.js`](config/industry.js).

The result: the base industrial cohort runs ~5.3% modelled absence,
manufacturing ~3.6% (lighter, more stable), logistics ~7.9% (long hours, worse
sleep, driver-fatigue), hospitality ~4.7% (younger and lower metabolic load, but
the heaviest fatigue after logistics) - the same model scoring four different
populations.

### Hospitality

Hospitality is the first version outside heavy industry, so it changes the
costing as well as the population. Absence is priced at a lower day rate
(R650), cover is bought from casual and agency staff at a premium (R260 a
cover-day) rather than overtime, and more absences must be covered (95% in the
highest-load cohort), because a short kitchen or floor slows the whole service.
These live in `SECTOR_ECONOMICS` in
[`model/build_sector_feeds.py`](model/build_sector_feeds.py) and pass through
`feed_enrich.enrich(..., economics=...)`; every other feed keeps the
heavy-industry defaults.

Every hospitality number is **directional and unsourced** until the calibration
sources are agreed: the cohort knobs, the day rate, the cover premium and the
benchmark heatmaps. The on-screen copy says "illustrative" rather than quoting a
benchmark for that reason. One more caveat: the model learned its relationships
from industrial data, where absence rises with age. In hospitality, younger
staff may well take more short absences, which the model would understate.

### Hospitality as a platform tenant

The platform can run as a hospitality tenant: the agents, Proposals and the
control centre then work on the hospitality cohort, with **departments**
(Kitchen, Front of house, Housekeeping, Front office, Maintenance, Support and
admin) as a grouping you can report on and target.

**On the demo, switch tenants in the header.** A synthetic demo that does not
pin a sector carries both demo groups, and the header offers
**Industrial | Hospitality** next to the currency toggle. The choice is a
cookie the server reads on every request, so every screen, every agent lookup
and every API route works on the group named in the header. Switching reloads
the page, and drafts held in the browser (interventions, playbooks, proposals)
are kept per group. The hospitality group has no sick-leave module, so its
links are gone and its URLs answer 404; switching from a sick-leave screen
lands on the overview. The rules are in
[`lib/platform/tenants.js`](lib/platform/tenants.js).

**A real deployment is one tenant, and the switch never appears there.** It is
hidden, and the cookie ignored, whenever any of these holds:

| Setting | Value | Effect |
| --- | --- | --- |
| `WELO_TENANT_SECTOR` | a sector, e.g. `hospitality` | Pins the deployment to that sector. The build carries its data alone, and fails if that data is missing rather than showing the base workforce under a hospitality name |
| `WELO_TENANT_SYNTHETIC` | `0` | Real data. The build carries the base workforce alone |
| `WELO_TENANT_SWITCH` | `0` | A demo that should show one group only |

No browser ever receives two groups' figures: every tenant's data stays on the
server, and screens that run in the browser get their one group's data as
props. A test fails if a client component imports tenant data.

A hospitality tenant drops the sick-leave module by default, because its sample
data is industrial (plants, depots, warehouses); `WELO_MODULE_SICK_LEAVE` still
overrides that. `WELO_TENANT_NAME` and `WELO_TENANT_DESCRIPTOR` still put a
prospect's name on a pinned deployment, but not on one that switches, where a
single name would sit on top of two different groups.

Departments come from the data, not the code: a feed whose cohort has a
`department` column gets a `cohort_department` grouping, cover priced by
department, and a department table on the operations screen. Feeds without one
are unchanged. Department is targetable by default, because it is where people
work, which is what a roster or cover action is aimed at.

The hospitality tenant also has a **Demand and cover** screen
(`/absence/demand`): how busy each department is across a year, a month, a week
and a day, beside how much of its staff is expected to be off, with the pressure
points where both are high. Demand is a benchmark pattern for the sector until a
client's till, booking or occupancy data is connected, and the screen says so.
The patterns live in `SECTOR_DEMAND` in `model/build_sector_feeds.py` and the
logic in [`model/demand.py`](model/demand.py). The Planner reads the same
figures through the `read_demand` tool.

And a **Roster check** screen (`/absence/roster`). It applies the same rules to
everyone on a roster and counts, by department, the people with a shift that
breaks one. The rules come in two kinds:

- **Legal minimums,** citing their sources: a 12-hour daily rest and a 36-hour
  weekly rest (BCEA s15 and Sectoral Determination 14, cl 17), and a 45-hour
  ordinary week. A breach is a flag to check against any written agreements,
  not a finding and not legal advice.
- **Fatigue policy:** a late close then an early open, split shifts, runs of
  late finishes, and changes at short notice.

The demo checks an example roster generated from the tenant's own departments.
A roster loaded as CSV is read in the browser and never sent anywhere. A
roster with a column that identifies people (name, email, ID number) is
refused, and no staff reference ever comes back from the check. The Planner
reads the same counts through `check_roster`. Rules:
[`modules/absence/roster.js`](modules/absence/roster.js).

And a **Cost of short staffing** screen (`/absence/cost`). It puts money on the
gaps, keeping three kinds of figure apart:

- **Cover spend:** what cover cost, a single figure, because it was paid.
- **Lost revenue:** an estimate, always a range. Each short-staffed service is
  compared with fully staffed services at the same property, for the same
  service, on the same kind of day, within 90 days, with planned demand
  within 10%. What they took per unit of demand, times this service's demand,
  is what it should have taken; the gap is the loss.
- **Service indicators:** for departments whose short shifts do not show up in
  revenue (rooms turned late, jobs deferred). Counted, never priced.

Value at risk for the next 90 days is the cover the coming gaps will need plus
the revenue they will lose: shifts rostered to the demand pattern, absences at
the model's rates (allowing them to be off by about 10%), simulated 400 times,
each run priced with one draw of the revenue lost per short shift.

The history is synthetic until a client's attendance, trading and agency
invoice data is connected: 24 months for 20 properties, about 190,000 shifts.
The shape of the group is inferred from published norms, cited beside each
value in `SECTOR_STAFFING`: four-star properties of about 250 rooms at 1.2
staff per room, food and beverage at about 40% of rooms revenue (R42m a
property, from 2025 four-star rates and occupancy), breakfast strong and lunch
the weakest service, and 14 to 18 rooms per room attendant shift.
Because it is generated, the true loss is known, and the screen shows how close
the method came. Two things that check caught are now part of the method:

- **Comparators are matched on planned demand, not measured demand.** Picking
  them on noisy measured demand favours services whose demand was
  over-measured, which look less productive; that alone understated the loss
  by 2% to 7%, depending on how much demand varies.
- **The range is a shared-weight bootstrap.** Short services near each other
  lean on the same comparators, so their errors move together. Resampling each
  one separately gave a range far too narrow for a total. Across ten fresh
  histories the truth now falls inside the 80% range eight times, and the
  estimate averages 100.2% of it.

About 3% of short services find too few comparators and are left out, so the
estimate is a floor. Nothing is keyed by person: the history holds shifts and
services, never staff. Both agents read the figures through
`read_staffing_cost`, which returns every estimate as a range. Method:
[`model/staffing_cost.py`](model/staffing_cost.py); settings in
`SECTOR_STAFFING` in `model/build_sector_feeds.py`.

To rebuild the hospitality data: `python model/build_sector_feeds.py` and
`python model/build_outcome_series.py hospitality`.

### Currency

Amounts are stored in Rand and converted on the fly. A **ZAR / USD** toggle in
the header switches every figure (headline, cohort, individual, HR, ROI) at once;
`?currency=usd` sets it from a link. Both dashboards have it: the standalone one
and the platform shell.

The rate carries the date it was taken, and that date is shown beside the
figures whenever dollars are on screen. Set the two together or neither is
used, because a current rate next to a stale date is how a converted figure
ends up carrying somebody else's date.

| | Standalone dashboard | Platform shell |
| --- | --- | --- |
| Set the rate | [`config/industry.js`](config/industry.js), `WELO_FX = { zarPerUsd, asOf }` | `WELO_FX_ZAR_PER_USD` and `WELO_FX_AS_OF` |
| Formatter | `money()` in `index.html` | [`lib/platform/currency.js`](lib/platform/currency.js) |

In the platform, money renders through the `<Money zar={...} />` leaf rather
than a string helper, so a server-rendered screen converts without becoming a
client component. There is deliberately no Rand formatter left in
`modules/sick-leave/format.js`: a screen that builds its own `"R" + number`
renders a figure the toggle cannot reach, and CI fails on one.

The agents are not given the rate. They reason in Rand, the stored unit, and
the panel says so beside the answer when dollars are on screen, rather than
asking a model to do arithmetic whose result would be stated in confident
prose.

### Switching versions

Client links carry no visible switcher. To flip between versions yourself (for
previews or live in a meeting), add `&preview=1` (or `?preview=1`) to the URL,
e.g. `index.html?industry=generic&preview=1`. A small industry dropdown then
appears in the header; it never shows on the plain client links.

## What the dashboard shows

The dashboard is organised around **cohorts**, not sites. The model's signal is
operational and clinical (fatigue/burnout, smoking + alcohol load, metabolic
load, workload), so the workforce is grouped by the levers Welo can actually act
on rather than by geography.

- **Portfolio** - model-level headline: covered lives, predicted absent days
  (90d), cost exposure, addressable saving, risk distribution, fatigue/burnout
  segment, driver concentration, and a cohort summary table.
- **Cohorts** - group the covered workforce by **operational load**, **fatigue
  band**, **age**, **tenure** or **lifestyle risk**. Each cohort card shows its
  high/critical concentration, days per head, mean fatigue, cost exposure and
  addressable saving. Click a cohort to drill in.
- **Individuals** - the model scores every covered life. High and critical
  employees are listed first. Filter by risk band or cohort, sort, search, and
  click any row to open a profile drawer with the full prediction: risk-band
  probabilities, fatigue score, the drivers behind the prediction (SHAP where
  available, otherwise the model features sitting above the cohort norm), the
  employee's profile, and their cohort memberships.
- **HR & Ops** - the operational view for the HR team: predicted absence
  rate, shift cover-gap days and overtime backfill cost, absence frequency
  (Bradford-style), return-to-work caseload and leave hygiene, broken down by
  operational cohort, plus an HR action playbook. Cost and spell assumptions
  are benchmark-anchored and documented in the feed's `hr_ops.assumptions`.
- **Outcomes & ROI** - projected addressable saving, seasonality and an
  intervention scenario.

> The individual records are synthetic industrial workforce rows, not real
> people, and no client data was ever used to produce them. Every synthetic row
> is tagged `synthetic_industrial_v1__sa_shift_workforce` so it can be swapped
> for real client data without touching the dashboard. On the calibration
> anchor, precisely: the input distributions are anchored to published South
> African mining-cohort epidemiology, because that is the best-documented
> published source for a South African frontline workforce on a shift roster.
> The demo presents it as an industrial workforce, which is a reasonable stand-in
> across heavy industry, and the model card says what the anchor is rather than
> implying a broader evidence base than exists.

### Why cohorts instead of sites

Three reasons, open to challenge:

1. **The model has no site signal.** It predicts from health, fatigue and
   workload features. Cohorts defined on those features line up with where the
   absence actually concentrates, e.g. the *smoker + drinker* cohort runs a
   33% high/critical share vs 3% for *low lifestyle risk*; *high-intensity ops*
   runs 22% vs 6% for *light duty*. Site-level cuts wash that out.
2. **Cohorts map to interventions.** A high-fatigue or high-overtime cohort has
   an obvious rostering/clinical response; "Site 2" does not.
3. **Site data may not exist on day one.** Cohorts are derivable from the feed
   the model already produces, so the view works before any HR/location join.

When real site/department fields arrive they become just another cohort lens;
the Cohorts screen already supports multiple dimensions.

## AI agents (Anthropic API)

The dashboard can host three genuinely AI-powered agents that reason over the
model output: an **Analyst** (portfolio questions), a **Case Assistant** (drafts
a support and return-to-work plan for an individual), and a **Cover
Coordinator** (turns cover-gap and overtime into rostering actions). They are
powered by the Anthropic Messages API.

The API key must stay server-side, so the agents run inside the existing
`welo_inference` FastAPI service (`ANTHROPIC_API_KEY`), and the dashboard calls
that proxy over HTTP through [`config/agents.js`](config/agents.js). Point a
link at a deployed proxy with `index.html?api=https://<service-url>`. With no
proxy configured the dashboard falls back to built-in, non-AI summaries, so the
shareable static build never breaks.

The Case Assistant is wired into the Individual profile screen as the reference
integration. Full architecture, environment variables, endpoints and cost are
in [`model/welo_inference/AGENTS.md`](model/welo_inference/AGENTS.md).

### Agents that look things up and draft actions (platform)

In the Next.js platform, an agent can now call tools instead of answering in
one shot from what the browser sent. This is the groundwork for agents that act
rather than only explain, and it is agent-agnostic: whichever agents survive
the redesign run on it.

| Piece | File | What it holds |
| --- | --- | --- |
| Tool rules | [`lib/platform/agentTools.js`](lib/platform/agentTools.js) | Every tool names its permission, validates the model's input, and has its output screened: a person's identifier or a figure for a suppressed cohort withholds the whole result |
| Tool-use loop | [`lib/platform/agentLoop.js`](lib/platform/agentLoop.js) | Runs tools until the agent answers, sends thinking blocks back intact, answers every tool call, and stops after six rounds with tools switched off for the last |
| Recommendations | [`modules/control-centre/recommendations.js`](modules/control-centre/recommendations.js) | A priced, cohort-level action an agent drafts and a person decides. The requester cannot approve their own draft, a rejection needs a reason, and the track record says when it has too few cases to judge |
| Absence tools | [`modules/absence/agentTools.js`](modules/absence/agentTools.js) | Read tools over the same allow-listed figures the screens show, plus `draft_recommendation` for the Cover Coordinator only. There is no tool that approves, books or sends |
| Decisions | [`app/api/control-centre/recommendations/route.js`](app/api/control-centre/recommendations/route.js) | Approve, reject or close a recommendation, with the role checks run server side |
| Proposals screen | [`modules/control-centre/screens/ProposalsScreen.jsx`](modules/control-centre/screens/ProposalsScreen.jsx) | `/control-centre/proposals`: each proposal priced as saving, cost and net, the decision with its reason, the outcome once the horizon has passed, and the track record. Amounts follow the ZAR / USD toggle, and an outcome typed in dollars is stored in Rand |
| Proposals store | [`modules/control-centre/recommendationStore.js`](modules/control-centre/recommendationStore.js) | Browser-local, like playbooks. A draft cannot arrive decided, a status only moves forward one step, and the prediction cannot be edited after drafting. Five labelled examples show the full cycle with no agent key |

When the Cover Coordinator drafts something, the agent panel lists it as
"drafted for a decision, not yet approved" and saves it to Proposals. The panel
also shows which tools the answer was built from. Drafting is only offered when
the control centre is on for the tenant, so a draft always has somewhere to go.

Tools read the module data on the server, never the request body, so a
tampered request cannot change what the agent is told. Routes that pass no
tools answer exactly as before, and with no API key every agent still falls
back to the built-in summaries.

## The model (`model/`)

`model/` is the full absenteeism stack: a config-driven training pipeline
(`welo_pipeline`), a FastAPI inference service (`welo_inference`), trained
artifacts (`models/`), and the cached dashboard feed (`data/outputs/`). See
[`model/MODEL_README.md`](model/MODEL_README.md) for the pipeline, the inference
service, and the Cloud Run deployment.

Model performance (cross-validated, from `model/reports/model_metrics.json`):
regression CV R² ≈ 0.39 / MAE ≈ 6.2 hours; classification CV ROC-AUC (macro OvR)
≈ 0.85.

### Roster patterns in the model

The model sees how people were rostered, not only how long they worked. Four
features cover the last 28 days, and they are the same patterns the roster
check flags, so a manager who fixes a flagged roster moves exactly these inputs:

| Feature | What it counts | Roster check rule |
| --- | --- | --- |
| `short_rest_count_28d` | Gaps under 12 hours between shifts | Daily rest |
| `late_finish_share_28d` | Share of shifts ending at or after 22:00 | Late runs, late then early |
| `split_shifts_28d` | Days worked as two blocks with a 2-hour gap or more | Split shifts |
| `short_notice_changes_28d` | Shift changes made with under 48 hours notice | Short notice |

Each has a what-if lever (`short_rest_delta`, `late_finish_pct`,
`split_shifts_delta`, `short_notice_pct`), so the scenario engine can price a
roster fix the same way it prices an overtime cut. The definitions and effect
sizes live in one place, [`model/welo_pipeline/roster.py`](model/welo_pipeline/roster.py),
shared by the generators, the series builder and the feature pipeline.

Three things keep this honest:

- **Directional, not sourced.** The synthetic data says a short rest adds a
  little fatigue; it does not say how much it adds in any real workforce. Real
  roster history replaces the effect sizes.
- **Calibration held.** Effects are measured against a reference roster (the
  typical heavy-industry pattern), so the base cohort's average fatigue is
  unchanged and model accuracy is the same as before.
- **Missing roster data is neutral.** An extract without roster columns sits at
  the reference roster and contributes nothing, so the model falls back to the
  hours-based picture rather than inventing a roster story.

Sectors and hospitality departments carry their own patterns in
`model/sector_cohorts.py`: hospitality rosters are worse than the reference
(late closes, split service shifts, changes when bookings move), manufacturing
better, and within hospitality the kitchen and front of house sit well above
housekeeping and support.

## Regenerating the dashboard feed

The base feed (headline, risk distribution, fatigue, intervention queue with
SHAP reasons, global importance, metrics) comes from the training pipeline:

```bash
cd model
python -m welo_pipeline --config configs/demo.yaml
```

The dashboard additionally needs **cohort aggregates** and **per-individual
records**. Those are added by `model/build_cohort_feed.py`, which reproduces the
deterministic synthetic cohort (seed 7, n=5800, validated to match the
predictions 1:1 on actual absence hours), joins it to `predictions.csv`, derives
the cohort dimensions, and writes the enriched `dashboard_feed.json` / `.js`:

```bash
cd model
pip install numpy pandas pyyaml
python build_cohort_feed.py
```

The **sector feeds** (manufacturing, logistics, hospitality) are generated by
`model/build_sector_feeds.py`. It builds a sector-calibrated synthetic cohort
(`model/sector_cohorts.py`), scores it with the **same persisted model** as the
base cohort (one model, different populations: only the input distributions
change),
and runs the shared enrichment (`model/feed_enrich.py`) to write
`dashboard_feed.<sector>.js` for each sector. Global
feature importance and metrics are reused from the trained model; SHAP per-row
reasons are omitted for the sector cohorts, so the dashboard shows indicative
drivers there.

```bash
cd model
pip install numpy pandas pyyaml scikit-learn joblib
python build_sector_feeds.py
```

After retraining, rebuild every committed output in this order, because each
step reads the one before it:

```bash
cd model
python -m welo_pipeline --config configs/demo.yaml
python build_cohort_feed.py
python build_sector_feeds.py
python build_outcome_series.py
python build_outcome_series.py hospitality
python export_synthetic_extract.py
```

The sector calibrations in `sector_cohorts.py` are illustrative, anchored to
plausible SA sector norms, and stay illustrative until real client data lands.

The two illustrative benchmark panels are also sector-specific: the clinical
heatmaps (driver concentration, chronic-disease hotspots) and the seasonality
panels (52-week calendar, quarterly bars, addressable-saving-by-driver) are
re-skinned per sector from the `benchmarks` block in
[`config/industry.js`](config/industry.js): e.g. manufacturing leads on
musculoskeletal + metabolic with a post-festive production ramp, logistics on
metabolic + sleep/fatigue with a festive peak-season spike. Industrial, mining
and generic keep the static markup. These tables are illustrative benchmarks, not model
output.

The absence module has two agents of its own, a Portfolio Analyst on the
portfolio screen and a Cover and Roster Coordinator on HR and operations, at
`/api/absence/agent`. They use the shared prompts in
`model/welo_inference/agent_prompts.json` rather than the sick-leave-specific
ones, which name entitlement burn and ICD-10 chapters that this module's data
does not have. There is deliberately no Case Assistant here: the module's data
carries no individual records, so an agent that reasons over one person has
nothing to read.

Their grounding is an allowlist, in `modules/absence/context.js`. A cohort
below the suppression threshold is stripped before the payload exists, and
absence frequency and Bradford scores are withheld entirely, because an agent
given an attendance measure without the screen's copy around it reads it as a
ranking of who is absent most often.

The chronic-disease hotspots panel also exists in the platform shell, on the
absence Portfolio screen, carrying the dashboard's shipped-default figures
byte for byte so the two surfaces cannot quote different numbers at the same
prospect. Its data and its column control live in
[`modules/absence/data/chronic.js`](modules/absence/data/chronic.js), kept out
of the generated `portfolio.js` so a hand-written benchmark and pipeline
output never share one object. The platform version adds one control the
standalone does not have: columns are derived from the live cohort list, and a
cohort under the suppression threshold is dropped rather than greyed, because
a greyed column still puts a health prevalence beside the name of a group too
small to report on. The driver-concentration heatmap has not been ported.

Then reopen `index.html`.
